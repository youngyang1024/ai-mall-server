## 精彩提问：
既然Embedding不仅仅只是在前期建设知识库会用到，在后续的每轮对话问答也会先基于用户问题进行Embedding，再去知识库检索，我想了解下这个过程，是怎么把用户的一个问题转为向量再去检索知识库，再转为promt给LLM的，
比如用户咨询：我想买个原木风沙发。 这个过程我们会做什么？向量本质应该是基于余弦相似度算法给每个知识库算好了一个向量(0-1之间的值，可以理解为概率？相似度？)，那在“我想买个原木风沙发”这句话中，是把哪里字拆分了向量？
去检索是怎么检索的？类似于SQL的 where keyword =# and order by 相似度 desc 这样吗？

## 回答
这个问题问到 RAG 最核心的机械原理了，而且你的两个直觉——"0-1 之间的相似度"和"类似 SQL 的 where + order by"——一个说对了一半，一个几乎全对。我把"我想买个原木风沙发"这句话的完整旅程走一遍，途中顺手纠正那半个偏差。

## 先纠正一个关键误解：向量不是"一个值"，是"一组坐标"

你说"给每个知识库算好了一个向量（0-1 之间的值）"——不对。**每个文档存的向量是 1024 个数字组成的数组**（bge-m3 的维度），不是一个分数：

```
"北欧原木风三人沙发，白蜡木框架..." → [0.021, -0.13, 0.87, ..., 0.04]  ← 1024 个数
```

**0-1 之间的那个"相似度分数"不是预先存好的，而是查询时刻现算出来的**。逻辑关系是：

- 建库时（提前做）：每个文档 → 各自的 1024 维向量，存进向量库
- 提问时（现场做）：问题 → 问题自己的 1024 维向量 → 拿它和库里**每个**文档向量算一次余弦相似度 → 才得到一批 0-1 的分数

为什么必须现算？因为相似度是"问题和文档**之间**"的关系，问题没来之前，这个分数根本不存在。可以类比：每个文档的向量是它在"语义地图"上的**坐标**（提前标好），相似度是你此刻站的位置到各点的**距离**（你到了才能量）。

## 第一步：整句话变一个向量，不是拆字

你问"是把哪里的字拆分了向量"——**不拆。整句话进模型，出来一个向量**。

内部过程（这是 Embedding 模型自己干的，我们只是调 API）：

1. **分词（tokenize）**："我想买个原木风沙发" → `[我, 想, 买, 个, 原木, 风, 沙发]` 这样的 token 序列（bge-m3 用自己的分词器，切法不完全按汉语词典）
2. **Transformer 编码**：每个 token 先有个初始向量，然后经过几十层注意力机制**互相"看"**——"原木"看到了旁边的"风"，就知道这里说的是装修风格而不是木材原料；"沙发"看到"买"，知道这是购买意图
3. **池化（pooling）**：把所有 token 的向量汇总成**一个** 1024 维向量，代表整句话的意思

第 2 步是精髓：**向量是"整句话在上下文中的含义"，不是字词的简单叠加**。这就是为什么"原木风沙发"能和"北欧实木沙发"匹配上——它们字面几乎不重叠，但在语义地图上是邻居。也是 LIKE '%原木风%' 永远做不到的事。

对我们来说这一步就是一次 HTTP 调用：

```
POST https://api.siliconflow.cn/v1/embeddings
{ "model": "BAAI/bge-m3", "input": "我想买个原木风沙发" }
→ 返回 [0.018, -0.11, 0.79, ...]   // 1024 维
```

## 第二步：检索——你的 SQL 直觉基本是对的

把余弦相似度想象成一个函数 `cos_sim(v1, v2)`（两个向量夹角的余弦，方向越一致越接近 1），那检索**在语义上**等价于这条 SQL：

```sql
SELECT doc_id, content, metadata,
       cos_sim(doc_vector, :query_vector) AS score   -- 现场计算
FROM   vector_store
WHERE  metadata.type = 'PRODUCT'          -- ① 元数据过滤（这里才是真·where）
  AND  metadata.status = 'ON_SHELF'       --    下架过滤，精确匹配
  AND  cos_sim(...) >= 0.5               -- ② 相似度阈值（太不相关的不要）
ORDER BY score DESC                       -- ③ 按相似度排序
LIMIT 4                                   -- ④ top-K
```

和你写的对比，两处修正：

- **没有 `where keyword = #`**——关键词等值匹配整个被 `cos_sim` 排序取代了，这正是"语义检索"和"关键词检索"的分界线。`WHERE` 仍然存在，但只用于**元数据**（类型/上架状态），干的是精确过滤的活
- `order by 相似度 desc` ——**完全正确**，你已经抓住本质了

在 Spring AI 里这条"SQL"长这样（P1 你会亲手写）：

```java
vectorStore.similaritySearch(SearchRequest.builder()
    .query("我想买个原木风沙发")     // 框架内部自动调 Embedding
    .topK(4)
    .similarityThreshold(0.5)
    .filterExpression("type == 'PRODUCT' && status == 'ON_SHELF'")
    .build());
```

一个诚实的补充：SimpleVectorStore 真的就是**遍历全部文档挨个算**（暴力扫描，等价于全表扫描没索引）——几百个文档毫秒级，无所谓。Milvus 这类专业库的核心本事之一就是 **ANN 索引**（近似最近邻，如 HNSW）：不逐个比对、用"语义地图上的高速公路网"直接逼近最近的点，百万级文档也能毫秒返回。这是"将来为什么换 Milvus"清单上的又一条。

## 第三步：组装 Prompt 喂给 LLM

检索回来的 top-4 商品文档，被拼进导购 Agent 的提示词：

```
[系统提示词]（来自 t_ai_agent_config，B 端可编辑）
你是 ai-mall 的导购助手……回复结构：共情开场 + 分层推荐 + 总结 + 快捷提问……

[检索到的参考资料]（← RAG 塞进来的部分）
1.（spuId=12）北欧原木风三人沙发：白蜡木框架，浅木色，布艺坐垫，售价 ¥849.99…
2.（spuId=35）日式实木沙发：橡木，原木色调，可拆洗…
3.…
4.…

[对话历史]（来自 Redis 短期记忆，最近 N 轮）

[用户问题]
我想买个原木风沙发

[约束]
只能推荐参考资料中出现的商品，输出商品时给出 spuId…
```

LLM 读完生成推荐语并给出选中的 spuId 列表 → 后端按 spuId 反查 V1 API 拿实时价格/图片/库存 → 组装成 `card` 事件推给前端（模型不产出价格数字，防幻觉——D9）。

## 全链路时序总览

```
用户："我想买个原木风沙发"
  │
  ├─① 硅基流动 bge-m3：整句 → 1024 维查询向量        （~100ms，一次 HTTP）
  ├─② 向量库：cos_sim 排序 + 元数据过滤 → top-4 文档  （本地，~毫秒）
  ├─③ 组装提示词：系统提示词 + top-4 资料 + 历史 + 问题
  ├─④ 中转站 Claude：生成推荐语 + spuId 列表           （~2-4s，主要耗时）
  └─⑤ 后端按 spuId 反查 V1 → card 事件 → SSE 推前端
```

记三句话就够了：**向量是坐标不是分数，分数是查询时刻现算的；整句进模型出一个向量，注意力机制让"原木风"被理解为风格而非木料；检索就是"元数据 WHERE + 相似度 ORDER BY + LIMIT K"，你那句 SQL 直觉换掉 keyword 等值匹配就是标准答案。**
